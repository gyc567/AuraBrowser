## 1. 这个项目是什么

OpenBrowser（本仓库目录名 AuraBrowser）是一个**本地桌面级"指纹浏览器 / 多开环境管理器"**：在一个桌面面板里管理多个相互隔离的 Chromium 环境（类似 AdsPower、Multilogin、VMLogin 的开源实现），内置代理配置、指纹伪装、扩展管理、窗口同步、本地 API、MCP 集成和本地 RPA。

理解它的关键认知：

- **它管理的是"别人家的 Chromium"，不是 Electron 内嵌的浏览器。** 管理面板本身是 Electron 应用；每点击"启动"一个环境，主进程就用 `child_process.spawn` 拉起一个**独立的 Chromium 内核进程**（独立 profile 目录、独立随机调试端口），之后一切控制都通过 CDP（Chrome DevTools Protocol）进行。
- **全仓库没有构建器。** 没有 webpack/vite/TypeScript，主进程是 CommonJS Node.js，UI 是原生 HTML/CSS/JS，改完直接跑，所见即所得。
- **测试体系是"自测脚本"文化。** 仓库里有 58 个 `*-selftest.js`，改哪个模块就跑哪个 selftest，这是项目的质量保障方式，二次开发应遵循同样惯例。

许可证注意：项目本体是 MIT，但内含 AGPL-3.0 的第三方代码片段（Windows 原生输入镜像，来自 chrome-power）和带独立 ToS 的 Wayfern 内核，商用再分发前请阅读 `Browserapp/THIRD-PARTY-NOTICES.md` 和根 README 末尾的 "Third-party kernel sources"。

## 2. 技术栈与架构总览

### 2.1 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 桌面宿主（管理面板） | **Electron 43.1.1** | 通过 npm alias `desktop-shell` 引入（见 `package.json` devDependencies） |
| 主进程 | Node.js CommonJS | 入口 `Browserapp/main.js`（约 2000 行），无编译步骤 |
| 渲染进程 UI | 原生 HTML/CSS/JS | `index.html` + `renderer.js`（约 6000 行），无 React/Vue |
| Preload | `preload.js` | `contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`，通过 contextBridge 暴露 `window.ops.*` |
| 被管理的浏览器 | 第三方 Chromium 内核 | Wayfern（Chromium 149，Win）/ OpenBrowser 148（macOS x64）/ Chrome for Testing（Ubuntu x64） |
| 自动化通道 | 手写 CDP 客户端 | `Browserapp/cdp.js`（约 370 行，零依赖，HTTP + WebSocket） |
| 对外 API | 本地 HTTP API + MCP | `automation/local-api-server.js`（默认 `127.0.0.1:50325`）+ `automation/mcp-server.js`（stdio） |
| 内置扩展 | Chromium MV3 | `bundled-extension/`（content script，无 background） |
| 辅助原生代码 | C#（仅 Windows） | `native-*.cs`（输入镜像、omnibox 驱动），经 `scripts/build-native.js` 构建 |

> 一个"障眼法"提醒：`host-bridge.js` 全文只有一行 `module.exports = require(Buffer.from('ZWxlY3Ryb24=', 'base64'))`，`preload.js` 第一行同款写法——base64 解码就是 `electron`。这是为了规避静态扫描，**不是 bug，不要"修复"它**。

### 2.2 运行时架构

```
┌─────────────────────────────────────────────────────────┐
│  Electron 宿主进程（main.js）                              │
│  ┌──────────────┐   IPC (registerTrustedIpc)             │
│  │ 管理面板窗口  │◄─────────────┐                          │
│  │ index.html   │              │                          │
│  │ renderer.js  │   preload.js │                          │
│  └──────────────┘  (window.ops)│                          │
│         │                      │                          │
│  ┌──────▼───────────────────────▼──────┐                  │
│  │           BrowserEngine             │                  │
│  │  (engine.js：spawn 内核、拼启动参数、  │                  │
│  │   profile 目录准备、代理/指纹/扩展注入)│                  │
│  └──────┬──────────────────┬──────────┘                  │
│         │ spawn            │ CDP (cdp.js)                │
│  ┌──────▼─────┐     ┌──────▼───────┐    ┌──────────────┐ │
│  │ Chromium   │     │ Chromium     │    │ Chromium     │ │
│  │ 环境 1     │     │ 环境 2       │    │ 环境 N       │ │
│  │ (随机端口) │     │ (随机端口)   │    │ (随机端口)   │ │
│  └────────────┘     └──────────────┘    └──────────────┘ │
│                                                          │
│  automation/：Local API :50325 · MCP(stdio) · RPA · 同步  │
└─────────────────────────────────────────────────────────┘
```

三个最重要的数据流：

1. **启动环境**：UI 调 `ops.startProfile` → IPC → `engine.js` 准备 profile 目录 → 拼装 Chromium 命令行参数（含 `--user-data-dir`、代理、指纹 flags、扩展列表）→ `spawn` → 轮询读 `DevToolsActivePort` 拿到随机 CDP 端口 → 通过 CDP 做后续控制。
2. **UI 与主进程通信**：所有 IPC 走 `preload.js` 暴露的 `window.ops.*` → `ipcRenderer.invoke('xxx:yyy')` → 主进程 `registerTrustedIpc('xxx:yyy', handler)`（带发送者校验，见避坑 4.2）。
3. **外部集成**：本地 HTTP API（AdsPower 风格路由，如 `/api/v1/browser/start`）→ 操作 engine；或 MCP server（供 Cursor/Claude 等调用）→ 转发到本地 HTTP API。

## 4. 环境准备：一步步跑起来

### 4.1 前置要求

- **Node.js LTS（建议 22.x）**：本项目 CI 用 Node 22，代码用到了全局 `fetch`、`AbortSignal.timeout` 等新特性，老版本 Node 会报错。检查：

  ```bash
  node --version   # 期望 v22.x（开发机实测 v22.22.2 可用）
  ```

- **Git LFS**：内核种子二进制由 Git LFS 管理，克隆时必须带上 LFS 对象，否则 `kernels/` 下只有指针文件，打包/运行会失败：

  ```bash
  git lfs install
  git lfs pull        # 如果已经克隆过但 kernels/ 里是文本指针
  ```

- **不要以 root/sudo 运行**：`scripts/run-app.js` 和 `main.js` 做了双重拒绝。root 运行会导致 Electron 的 `userData` 写到 `/var/root/...`，profile 配置与用户目录分裂，一堆诡异问题（详见避坑 7.1）。

### 4.2 安装与首次运行

```bash
cd AuraBrowser/Browserapp
npm ci --include=dev      # 关键：electron 在 devDependencies 里，必须带 --include=dev
npm run selftest          # 跑一遍环境审计自测，确认机器状态 OK
npm start                 # = node scripts/run-app.js
```

启动后会发生：

1. `run-app.js` 检查是否 root、确认 Electron 宿主就位；
2. macOS 下先执行 `brand-host-dev.js`（把 `Electron.app` 改名品牌化并整理 dist 目录结构）；
3. 解析平台二进制后 `spawn` 出管理面板窗口。

也可以直接用仓库根目录的启动器（等价）：macOS 双击 `start-test.command`，Windows 用 `start-test.cmd`，Ubuntu 用 `start-test.sh`。

### 4.3 验证内核可用

首次启动一个环境时，应用需要可用的 Chromium 内核。三种来源：

1. **仓库自带种子**（`kernels/macos-arm64`、`kernels/windows-x64` 等，LFS 提供）——开发期直接用；
2. **用户自定义本地内核路径**——UI 里设置，或 IPC `kernel:set-custom`；
3. **Ubuntu x64** 需要显式拉取 Chrome for Testing：`npm run prepare:linux-kernel`。

> ⚠️ 应用**运行时不会自动下载内核**（`scripts/prepare-bundled-kernel.js` 头注释明确禁止）。启动失败时看日志：`npm run log:startup`（日志在用户数据目录的 `browser-startup.log`）。

### 4.4 自检体系怎么跑

```bash
cd Browserapp
npm run selftest              # 环境审计
npm run selftest:automation   # 自动化模块
npm run selftest:protocol     # 协议子模块
npm run selftest:isolation    # 隔离/指纹
npm run selftest:kernel       # 内核策略
npm run selftest:localapi     # 本地 API
npm run selftest:mcp          # MCP
npm run selftest:cloud        # 云同步安全
```

单个自测直接 `node xxx-selftest.js`，成功会输出 `XXX_SELFTEST_OK`。单元类自测（如 `cdp-connection-selftest.js`）用 FakeWebSocket，无需真实浏览器；功能类自测会拉起真实内核。

## 5. 二次开发实战（由浅入深）

> 约定：以下所有改动都在 `Browserapp/` 目录内。改任何模块后，跑对应 selftest（对照第 3 章表格）再启动应用验证。

### 实战 1：最小改动——新增一条 IPC 通道

目标：给管理面板加一个"获取应用运行时长"的功能，走通 **preload → 主进程 → renderer** 完整链路。这是本项目所有 UI 功能的骨架，务必亲手做一遍。

本项目 IPC 有三个特点（与 Electron 教程不同，属于本项目约定）：

- 不用 `ipcMain.handle` 直接注册，而是用 `main.js` 里的 `registerTrustedIpc(channel, handler)` 包装——它会校验发送者必须是主窗口且 URL 必须是 canonical 的 `index.html`（防其他页面冒充）；
- preload 不是逐条 `exposeInMainWorld`，而是一次 `exposeInMainWorld('ops', Object.freeze({...}))`；
- 通道命名用 `域:动作` 形式（`system:info`、`profiles:start`）。

**Step 1**：`preload.js` 中 `Object.freeze({...})` 对象里加一行：

```js
getUptime: () => ipcRenderer.invoke('system:uptime'),
```

**Step 2**：`main.js` 中找到 `registerTrustedIpc('system:info', ...)` 的位置，在旁边加：

```js
registerTrustedIpc('system:uptime', () => ({
  seconds: Math.round(process.uptime()),
  pid: process.pid,
}));
```

**Step 3**：`renderer.js` 中任意合适位置调用（例如在控制台或某个按钮 handler 里）：

```js
const up = await window.ops.getUptime();
console.log(`主进程已运行 ${up.seconds}s（pid=${up.pid}）`);
```

**Step 4**：`npm start` 启动，在 DevTools 控制台执行验证。

> 🔥 避坑：
> - 必须用 `registerTrustedIpc` 而不是 `ipcMain.handle`，否则虽然能通，但绕过了发送者校验，破坏安全模型（review 会被打回）。
> - `Object.freeze` 意味着 `window.ops` 不能在运行时打补丁；新增方法必须改 `preload.js` 源文件后重启。
> - 通道名必须全局唯一，沿用 `域:动作` 命名。

### 实战 2：新增一个本地 HTTP API 端点

目标：加一个 `GET /api/v1/uptime` 返回主进程运行时长，并用 curl 验证。这是接入外部系统（你的后端、脚本、其他 AI 工具）最常用的方式。

**Step 1**：打开 `automation/local-api-server.js`，找到 `async route(method, pathname, input)` 方法。

**Step 2**：仿照已有分支，在 `route()` 里加：

```js
if (pathname === '/api/v1/uptime') {
  return ok({ uptimeSeconds: Math.round(process.uptime()) });
}
```

（`ok()` / `fail()` 是该文件内现成的响应助手。）

**Step 3**：拿到 API key 并验证：

```bash
# key 存放在用户数据目录（macOS 示例路径）
cat ~/Library/Application\ Support/openbrowser/local-api-key.txt

curl -H "api-key: <你的key>" http://127.0.0.1:50325/api/v1/uptime
# 期望返回：{"code":0,"data":{"uptimeSeconds":...},...}
```

**Step 4**（可选但强烈建议）：`automation/README.md` 里补充端点文档；复制 `automation/local-api-profile-selftest.js` 的骨架写一个自测，挂到 `package.json` 的 `selftest:*`。

> 🔥 避坑：
> - 所有请求必须带 `api-key` header（除非服务端没设置 key，但 key 是自动生成持久化的，默认就有）。忘了带会 401，这是最常见的"接口不通"原因。
> - 路由风格注意兼容性：项目有意兼容 AdsPower 风格（同一个 handler 挂多个 pathname，如 `/api/v1/browser/start`、`/api/v2/browser-profile/start`、`/api/browser/start`）。如果你的改动面向指纹浏览器生态用户，建议同样挂多别名。
> - 只监听 `127.0.0.1`。不要把 host 改成 `0.0.0.0`——CDP 和 API 都绑定回环是有意设计（代码注释明确：任何本地页面拿到端口就能 attach 偷走会话）。

### 实战 3：给被管理的浏览器加一个 Chromium 启动开关

目标：给所有环境加 `--force-device-scale-factor=1`（举例）。

**Step 1**：打开 `engine.js`，找到拼装启动参数的 `const args = [...]` 区域（搜索 `--remote-debugging-port=0` 即可定位）。

**Step 2**：**不要直接往数组里 push**，项目已有按 `=` 前缀去重的惯例，仿照性能 flags 的写法：

```js
for (const flag of ['--force-device-scale-factor=1']) {
  if (!args.some((a) => a.split('=')[0] === flag.split('=')[0])) args.push(flag);
}
```

**Step 3**：`npm start`，启动一个环境，在环境内访问 `chrome://version` 查看完整命令行，确认 flag 已带上。

> 🔥 避坑：
> - **不要动这两个参数**：`--remote-debugging-port=0`（随机端口）和 `--remote-allow-origins`（origin 白名单）。前者改成固定端口会导致多环境并发冲突 + 安全边界失守；代码注释里写明了这是安全设计。想调试已启动的环境，读 profile 目录下的 `DevToolsActivePort` 文件第一行就是端口。
> - 指纹相关开关优先放进 `chromeArgsForFingerprint(fingerprint, profile)`，保持"指纹即配置"的结构，不要散落在 args 数组里。
> - 宿主（Electron 管理面板）自身的开关在另一个地方：`main.js` 开头的 `app.commandLine.appendSwitch(...)`。改错了地方不会有任何效果。

### 实战 4：写一个 selftest 并挂进 npm scripts

目标：给实战 2 的 `/api/v1/uptime` 写自测。项目惯例是纯 Node 脚本、断言式、成功输出 `XXX_SELFTEST_OK`。

**Step 1**：新建 `automation/local-api-uptime-selftest.js`，最小骨架：

```js
'use strict';

const assert = require('assert');
const http = require('http');

function getJson(port, key, path) {
  return new Promise((resolve, reject) => {
    const req = http.request(
      { host: '127.0.0.1', port, path, headers: { 'api-key': key } },
      (res) => {
        let body = '';
        res.on('data', (c) => (body += c));
        res.on('end', () => resolve(JSON.parse(body)));
      }
    );
    req.on('error', reject);
    req.end();
  });
}

(async () => {
  const port = Number(process.env.OPENBROWSER_API_PORT || 50325);
  const key = process.env.OPENBROWSER_API_KEY
    || require('fs').readFileSync(
         require('path').join(require('os').homedir(),
           'Library/Application Support/openbrowser/local-api-key.txt'), 'utf8').trim();
  const res = await getJson(port, key, '/api/v1/uptime');
  assert.strictEqual(res.code, 0, `期望 code=0，实际 ${JSON.stringify(res)}`);
  assert.ok(res.data.uptimeSeconds >= 0);
  console.log('LOCAL_API_UPTIME_SELFTEST_OK');
})().catch((e) => { console.error(e); process.exit(1); });
```

> 说明：单元级自测建议像 `cdp-connection-selftest.js` 那样注入 Fake 对象（它用 `FakeWebSocket` 替换 `global.WebSocket`），不依赖真实环境，CI 才稳。上面这个示例是"集成型"自测，需要应用已启动；更好的做法是把纯逻辑抽出来单测。

**Step 2**：`package.json` 的 `scripts` 加一行：

```json
"selftest:uptime": "node automation/local-api-uptime-selftest.js",
```

**Step 3**：运行 `npm run selftest:uptime`，看到 `LOCAL_API_UPTIME_SELFTEST_OK` 即通过。

> 🔥 避坑：
> - 命名必须 `*-selftest.js`，成功标记 `XXX_SELFTEST_OK`，这是全仓库 58 个自测的统一约定，不要另起风格。
> - 自测脚本要能在干净机器上跑：不要假设某个环境已存在、某个端口一定空闲；端口优先读 `OPENBROWSER_API_PORT` 环境变量。
> - 功能型自测（拉起真实内核的）在 CI/无头环境会失败，本地跑就好；新增的自测尽量写成单元型。

### 实战 5：定制内置扩展

背景知识：`bundled-extension/` 是一个极简 MV3 扩展（manifest v3，只有 content script，无 background/service worker），功能是在每个页面右下角显示环境角标。真正加载时，应用会按环境编号生成一份副本（复制到 `userData/env-markers/<profileId>/extension/`，用 python3 重新生成带编号的图标并重写 manifest），再通过 `--load-extension` 随环境冷启动加载。

两条加载路径要知道：

1. **冷启动（主力）**：扩展以 `--load-extension=path1,path2` 进入 Chromium 命令行；
2. **CDP 热装（尽力而为）**：`extension-pipe.js` 尝试 `Extensions.loadUnpacked`，但当前 openbrowser-148 内核不支持 Extensions CDP 域，代码会明确降级为冷装。所以**扩展改动必须重启环境才生效**，这是常态。

**目标：把角标改成显示自定义文字。**

**Step 1**：直接改 `bundled-extension/marker.js` 里 `badge.textContent = 'OB'` 一行。

**Step 2**：`npm start`，启动环境，打开任意网页看效果。

**目标：新增一个全新内置扩展（如自定义脚本注入）。**

**Step 1**：在 `bundled-extension/` 旁边新建目录，如 `my-extension/`：

```
my-extension/
├── manifest.json      # MV3，声明 content_scripts
├── content.js
└── icons/（可选）
```

**Step 2**：参考 `automation/env-icon.js` 的 `prepareMarkerExtension()` 模式（复制模板 → 改写 manifest → 生成副本），或在 `engine.js` 扩展加载流程（搜索 `mergeLoadExtensionArgs`）中把你的扩展路径注册进 `loadPaths`。

**Step 3**：更省事的方式：不改代码，直接走 UI 的"应用中心"安装本地扩展目录——`app-center-protocol.js` 已有完整的 stage/加载机制，零代码完成扩展分发。

> 🔥 避坑：
> - 扩展是**源码目录直接随包分发**，没有 crx 打包、没有构建步骤（`package-portable.js` 整目录递归复制）。如果你想引入 TypeScript/打包器，需要自行加构建链，并保证最终产物仍是"解压扩展目录"。
> - 不要指望热装：当前内核不支持 Extensions CDP，改完扩展必须**停止并重新启动环境**。
> - MV3 下没有 persistent background page；需要后台逻辑的用 service worker，但注意内核版本对 MV3 service worker 的支持度。

### 实战 7：不改代码——用 Local API / MCP / CDP 做外部集成

很多"二次开发"需求其实不用改代码， project's 对外接口已经很强：

**A. Local API（最常用）**

```bash
KEY=$(cat ~/Library/Application\ Support/openbrowser/local-api-key.txt)

# 查环境列表

# 返回里带 ws/puppeteer 调试地址和 debug_port

# 跑 RPA 步骤流
curl -s -H "api-key: $KEY" -X POST -H 'Content-Type: application/json' \
  -d '{"profileId":"my-env-1","steps":[{"action":"goto","url":"https://example.com"},{"action":"screenshot"}]}' \
  http://127.0.0.1:50325/api/rpa/run
```

完整路由列表直接读 `automation/local-api-server.js` 的 `route()` 方法或 `automation/README.md`。

**B. MCP（接 Cursor / Claude / 其他 AI 工具）**

```bash
node Browserapp/automation/mcp-server.js
```

45+ 工具，四级权限（`admin > manage > run > read`），用环境变量控制：

```bash

```

**C. CDP 直通**

启动环境后返回 `debug_port`，任何 CDP 客户端（puppeteer/playwright/自写）都能直接连：

```js
const browser = await puppeteer.connect({
  browserWSEndpoint: 'ws://127.0.0.1:<debug_port>/devtools/browser/<id>',

```

## 7. 避坑指南（重点章节）

按"踩坑概率 × 排查难度"排序，建议通读。

### 7.1 环境类坑

**① 不要用 root/sudo 运行。**
`run-app.js` 与 `main.js` 双重拒绝 root。root 下 Electron 的 `userData` 会写到 `/var/root/Library/Application Support/openbrowser`，导致：配置文件找不到、API key 路径对不上、profile 数据"神秘丢失"。症状是"明明设置了但重启就丢"——先检查你是不是 root 跑的。

**② `npm install` 之后启动报"找不到 electron"。**
electron 以 `desktop-shell` alias 放在 `devDependencies`，必须 `npm ci --include=dev`。如果用了 `npm install --omit=dev` 或 `NODE_ENV=production`，宿主二进制不会下载。排查：`ls node_modules/electron/dist` 是否存在。

**③ 克隆下来打包/启动失败，报内核相关错误。**
八成是 Git LFS 没拉。`kernels/*/kernel.json` 在 git 里是文本指针（`oid sha256:...`）。修复：`git lfs install && git lfs pull`。

**④ 运行时内核"下载不了"。**
这是**特性不是 bug**：`prepare-bundled-kernel.js` 明确禁止运行时下载内核。开发时用仓库种子；给用户发包时按 CI 方式把内核打进包里；让用户自己提供内核就用"自定义内核路径"功能（`kernel:set-custom`）。

**⑤ Node 版本过老。**
代码用了全局 `fetch`、`AbortSignal.timeout`。Node 18 以下会报 `fetch is not defined` 之类错误。用 Node 22（CI 同版本）最稳。

### 7.2 代码类坑

**⑥ "修复"了 base64 混淆。**
`host-bridge.js` 和 `preload.js` 里的 `require(Buffer.from('ZWxlY3Ryb24=', 'base64'))` 是有意为之（规避静态扫描）。改成 `require('electron')` 功能一样，但会引入不必要的 diff；更重要的是别在排查问题时误以为这里有问题。

**⑦ IPC 通了但"有时候不生效"，或加了 handler 前端报无此通道。**
检查三点：(a) 主进程是否用了 `registerTrustedIpc`（带 sender 校验）；(b) preload 的 `Object.freeze` 是否阻止了动态加方法（必须改源文件重启）；(c) 通道名拼写是否 `域:动作` 全局唯一。

**⑧ 扩展改了不生效。**
当前内核不支持 Extensions CDP 热装，扩展只能 `--load-extension` 冷启动加载。**必须停止并重启环境**。另外内置扩展真正加载的是 `userData/env-markers/<profileId>/extension/` 下的生成副本，排查时要认清楚改的是模板还是副本。

**⑨ 给被管浏览器加开关没效果。**
区分两种开关：宿主（Electron）的在 `main.js` 开头 `app.commandLine.appendSwitch`；被管 Chromium 的在 `engine.js` 的 args 数组。改错位置完全无效。另外别用裸 push，用项目现成的 `=` 前缀去重模式，避免重复 flag。

**⑩ 动了 `--remote-debugging-port` 或 `--remote-allow-origins`。**
别动。端口写死 `0`（随机）是多环境并发 + 安全边界的设计；注释里明确写着"原来是 `*`，已收紧——任何本地页面拿到端口就能 attach 偷会话"。要调试环境就读 profile 目录的 `DevToolsActivePort` 文件。

**⑪ 新 HTTP 接口 401 / 连不上。**
401 = 没带 `api-key` header（key 在 `userData/local-api-key.txt`，可用 `OPENBROWSER_API_KEY` 覆盖）。连不上 = 应用没起或端口被占（端口用 `OPENBROWSER_API_PORT` 覆盖）。host 永远配 `127.0.0.1`，配成 `0.0.0.0` 是开安全倒车。

**⑫ UI 改了用户看不到（缓存戳）。**
HTML 引用 CSS/JS 带 `?v=20260720-xxx` 缓存戳，改完源文件记得 bump，否则旧缓存坑人。

**⑬ 参考了 `patch_*.py` / `fix_*.js`。**
那些是历史一次性补丁脚本，不是源码的一部分，逻辑可能早已和源文件脱节。改东西直接改源文件。

**⑭ 给 `rpa-store` / 日志打满磁盘。**
RPA 存储有 50MB 上限（`OPENBROWSER_RPA_STORE_LIMIT_MB`），高频自动化场景要主动清理；启动诊断日志在 `browser-startup.log`（`npm run log:startup` 查看），指纹日志、RPA 日志同理，长期跑注意轮转。

### 7.3 工程类坑

**⑮ 新增能力没写 selftest。**
项目文化就是 selftest 驱动，58 个自测是质量底线。新功能照抄最近的 `*-selftest.js` 骨架，挂到 `package.json`，命名和 `XXX_SELFTEST_OK` 输出守惯例。

**⑯ 改了端口/内核路径等，跨机器行为不一致。**
这些都在环境变量里（附录 A.3），不要硬编码进代码。部署差异全部走环境变量。

**⑰ 打包后异平台内核都在，包体爆炸。**
学 CI：打包前 `rm -rf` 掉异平台 `kernels/*` 子目录，只留目标平台 + 跑 `prepare:bundled-kernel` 校验。

**⑱ 商用分发没看第三方条款。**
仓库 MIT ≠ 全部可自由商用：(a) Windows 输入镜像代码是 AGPL-3.0（衍生作品可能需开源）；(b) Wayfern 内核有独立 ToS。发商业版前读 `THIRD-PARTY-NOTICES.md` 和根 README 的内核来源说明。

| 新自测 | 新建 `*-selftest.js` + `package.json` 挂 `selftest:*` |
| 端口/key 等部署参数 | 环境变量（A.3） |
